# 주문과 취소의 백엔드 점검

이 서버는 같은 구매의 재전송, 마지막 재고의 동시 주문과 반복 취소를 다룹니다. 주문을 한 번만 만들고, 주문 상태와 재고 및 이력을 함께 저장하는 것이 기준입니다. 기준 버전은 `6e74951`의 135건입니다.

## DB 중단 때 바로잡은 응답

DB가 꺼진 동안 계정 조회가 실패하면 기존 보안 필터는 잘못된 비밀번호와 같은 401을 반환했습니다. 인증 처리의 저장소 실패를 따로 구분해, 연결 장애는 기존 오류 형식의 503과 재시도 안내를 반환합니다. 인증을 생략하거나 실패한 요청을 주문으로 처리하지 않습니다.

커밋 직전에 DB를 중단하면 기존 JdbcTransactionManager의 커밋 오류 뒤 롤백 오류가 원인을 대체해 500으로 분류됐습니다. 원래 오류가 이미 사라진 경우에는 예외의 원인을 순회하는 것만으로 해결되지 않았습니다. DataSourceTransactionManager는 커밋 실패의 SQLException을 보존하고 실패한 커밋에 추가 롤백을 시도하지 않도록 설정했습니다. 재고 SQL, 함께 저장하는 데이터와 서비스의 격리 수준은 바꾸지 않았습니다.

DB 복구와 데이터 정합성은 수정 전후 모두 유지됐고, 잘못된 장애 응답을 바로잡았습니다.

연결을 잃은 커밋을 무조건 실패나 성공으로 단정하지 않습니다. 서버가 새 구매를 자동 생성하지 않으며, 고객은 같은 구매 키 또는 같은 취소 주문 ID로 결과를 확인합니다. [Spring 커밋 실패 처리](https://github.com/spring-projects/spring-framework/blob/v6.2.19/spring-tx/src/main/java/org/springframework/transaction/support/AbstractPlatformTransactionManager.java), [JDBC 트랜잭션 관리자](https://docs.spring.io/spring-framework/docs/6.2.19/javadoc-api/org/springframework/jdbc/datasource/DataSourceTransactionManager.html)

## 검증 구분

| 실행 | 확인 내용 | 결과 |
| --- | --- | --- |
| 일반 검사 | 기존 135건, 두 JVM 12건, 오류 분류/인증 응답 7건 | 154건 통과. JAR와 Javadoc 통과 |
| DB 중단 전후 | 주문/취소 커밋 직전 중단, 각각 확정 후 응답 유실, 인증 중 DB 중단. 각 3회 | 수정 전 15건 중 9건 실패, 수정 후 15건 통과 |
| 두 JVM | 같은 구매 20회, 마지막 재고, 같은 취소 20회, 취소와 새 구매. 각 3회 | 주문과 복구 중복 없음. 요청 한도는 여전히 JVM마다 별도 |
| 부하 | 1/8/32/64명, 같은 상품/100개 상품, 준비 10초와 측정 30초, 각 3회 | 개별 요청 원문 대신 k6 원시 지표와 실행별 DB 대조값 보관 |

DB 중단은 일반 JUnit과 분리한 로컬 검사입니다. 새 전용 DB의 경로와 포트를 확인한 뒤 `pg_ctl -m immediate`로 중단했습니다. `fsync=on`, `synchronous_commit=on`은 유지했고 서버 JVM도 유지했습니다. 같은 DB의 데이터 복구 검사이지 호스트 전원 장애나 저장 장치 고장 검사는 아닙니다.

확인한 수량 규칙은 `남은 재고 = 초기 재고 - 취소되지 않은 주문 수량 합계`입니다. 재고 증감 이력의 합계, 구매 결과와 주문의 연결, 주문별 차감/복구 횟수도 함께 대조합니다. [검증 기록](VERIFICATION.md)과 [대표 원시 결과](../evidence/verification/backend-review.json)를 확인해주세요.

압축 원시 지표 24개를 다시 읽어 성공 표본 30,298개와 p95가 k6 요약과 일치하는지 확인했습니다. k6의 HTTP 원시 기록에는 CSRF 조회 630건과 주문 성공 39,808건, 제한 거절 96건이 있습니다. 이 중 표에 집계한 측정 구간의 429는 34건입니다.

## 재현과 미검증 범위

```powershell
.\scripts\test.ps1 -IsolatedDatabase
.\scripts\test.ps1 -IsolatedDatabase -DatabaseRecovery -TestsOnly
node scripts/review-load.cjs --smoke
node scripts/review-load.cjs
```

부하 검사에는 [공식 k6 v2.3.0](https://github.com/grafana/k6/releases/tag/v2.3.0) Windows 압축 배포본이 필요합니다. `.tools/k6/v2.3.0` 아래에 배치하며 배포 ZIP의 SHA-256은 `112276d495e5741c968e2bc09ea6196099c1275bd6db9ee0875d173c7148ce43`입니다. 서버 쓰기 한도 32건과 연결 풀 12개는 유지하고, 측정 때만 고객별 분당 횟수를 100,000회로 높였습니다. 2초 smoke 실행은 성능 결과에 포함하지 않습니다.

운영 수용량, 장시간 부하, 여러 서버의 공통 요청 한도, 구매 기록 정리 후 재요청은 미검증입니다. 기존 API 경로와 JSON 필드는 유지했습니다. 기술을 더 넣는 대신 주문과 취소의 보장, 실패 시 처리와 설명 가능한 근거를 갖추는 데 범위를 뒀습니다.

요청 한도는 인증 후 주문과 취소 호출에 적용합니다. 인증 시도 자체의 부하는 제한하지 않습니다. 외부에 서비스를 공개할 때는 TLS와 인증 시도 제한을 별도로 설계해야 합니다. k6 결과에도 실제 Basic 인증 비용이 포함되므로 SQL만의 속도로 읽지 않습니다.
