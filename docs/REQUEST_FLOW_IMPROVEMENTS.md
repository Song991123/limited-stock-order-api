# 큰 요청의 조기 거절과 취소 한도 분리

## 우선순위와 수정 범위

| 우선순위 | 사용자 행동에서 확인한 조건 | 처리 |
| --- | --- | --- |
| 1 | 길이가 8KiB를 넘는다고 헤더에 적혀 있어도 본문 전송 시작 뒤 거절 | 헤더 선검사와 Tomcat의 100 Continue 응답 시점 변경 |
| 1 | 구매 재전송으로 고객별 횟수를 채우면 자기 주문 취소도 429 | 구매와 취소의 횟수 분리, 전체 동시 쓰기 제한은 공유 |
| 2 | SQL 오류/JVM 종료와 달리 DB 서버 자체 중단 뒤 재접속은 미검증 | 전용 DB의 중단/복구 뒤 같은 구매 키와 취소 결과 확인 필요 |
| 2 | 구매 결과가 계속 쌓이며 보존량 제한 없음 | 보존 기간과 만료 응답을 정한 뒤 정리. 삭제만 먼저 하면 오래된 키가 새 구매가 될 수 있음 |
| 3 | 잠금 대기와 방식별 처리량은 미측정 | 같은 입력의 부하와 잠금 대기부터 측정. 속도 근거 없이 Redis/다른 락으로 교체하지 않음 |
| 유지 | 기존 중복 요청과 취소, 롤백과 재시작에서 수량/이력 일치 | 재고 SQL, 유일성 제약과 트랜잭션 설정 유지 |

## 큰 요청을 읽기 전에 거절

클라이언트가 본문 전송 허용을 기다리는 `Expect: 100-continue` 요청을 보냈습니다. 길이는 8,221바이트로 한도를 넘었지만 기존 서버는 본문 전송을 시작시킨 뒤 413으로 거절했습니다. 주문은 저장되지 않았으나 불필요한 본문 전송은 시작됐습니다.

[RequestSizeFilter](../src/main/java/dev/mentoring/orders/web/filter/RequestSizeFilter.java)에서 알려진 길이가 8KiB를 넘으면 스트림을 열지 않고 거절합니다. 나머지는 기존처럼 최대 8KiB보다 한 바이트 더 읽어 검사합니다. 작은 길이 값만 보고 통과시키거나 chunked 검사를 생략하지 않습니다.

필터만 바꾸면 Tomcat이 먼저 100 Continue를 보낼 수 있습니다. [RequestBodyConfiguration](../src/main/java/dev/mentoring/orders/config/RequestBodyConfiguration.java)은 Tomcat의 `onRead` 설정으로 실제 본문을 읽을 때 전송을 허용합니다. 큰 길이는 먼저 거절하고 허용한 크기의 요청은 정상 전송합니다. 별도 HTTP 파서 대신 기존 컨테이너 설정을 사용했습니다. [Tomcat 설정](https://tomcat.apache.org/tomcat-10.1-doc/config/http.html), [HTTP Expect 규칙](https://www.rfc-editor.org/rfc/rfc9110.html#name-expect)

## 구매 한도와 취소 한도 분리

고객이 같은 구매를 재전송해 구매 한도에 도달한 뒤 취소했습니다. 기존 공통 카운터에서는 취소도 429여서 주문은 접수 상태이고 재고는 9로 남았습니다. 구매 재시도 때문에 취소를 못 하는 흐름을 바꾸기로 했습니다.

[WriteAdmission](../src/main/java/dev/mentoring/orders/web/admission/WriteAdmission.java)의 구매 카운터와 취소 카운터를 나눴습니다. `executeOrder`는 구매 횟수, `executeCancellation`은 취소 횟수를 셉니다. 두 처리는 같은 Semaphore로 전체 동시 쓰기 수를 제한합니다. 한도 초과와 실패 뒤에도 확보한 실행 자리는 반환합니다.

취소를 무제한으로 풀면 반복 취소가 DB를 계속 호출할 수 있어 취소에도 횟수 제한을 유지했습니다. 두 종류의 실행 자리를 따로 만들면 전체 동시 작업 수가 늘어나므로 Semaphore는 공유합니다. 기본 설정은 구매와 취소 각각 고객별 분당 120회이며 두 종류를 합쳐 동시에 최대 32건입니다. 계정별 허용 횟수의 합계는 이전보다 늘고 카운터도 두 개가 필요합니다. 운영 수용량이 늘었다는 뜻은 아닙니다.

## 전후 결과

| 조건 | 수정 전 | 수정 후 |
| --- | --- | --- |
| 길이 8,221바이트, Expect 요청 | 413, 본문 전송 시작 1회 | 413, 본문 전송 시작 0회 |
| 헤더의 길이가 8,193 또는 최대 long 값 | 스트림을 열어 읽음 | 스트림을 열기 전에 413 |
| 정상 크기의 Expect 요청 | 별도 전후 비교 대상 아님 | 전송 시작 1회, 201, 주문 1건 |
| 정확히 8,192바이트, 고정 길이/chunked | 둘 다 201 | 둘 다 201 |
| 구매 한도를 소진한 뒤 자기 주문 취소 | 429, 재고 9 | 200 CANCELLED, 재고 10, 복구 이력 1건 |
| 반복 취소도 취소 한도에 도달 | 별도 비교 대상 아님 | 429, 추가 복구 없음 |

수정 전 130건 중 새 조건 4건이 실패했습니다. 수정 후 같은 130건이 모두 통과했고 정상 전송과 한도 공유 등을 보는 5건을 더해 전체 135건이 통과했습니다. 검사 수 증가와 성능 개선율을 혼동하지 않습니다. [전후 원시 값 요약](../evidence/verification/request-flow-comparison.json)

전송 시작 횟수는 Java HTTP 클라이언트가 본문 발행기를 구독한 실제 횟수입니다. 모든 클라이언트의 전송 바이트나 응답 속도를 측정한 결과는 아닙니다. 이미 본문을 보내는 클라이언트와 길이를 모르는 요청은 서버가 일부 바이트를 읽을 수 있습니다.

기존 동시 주문, 같은 구매 20건 재전송, 반복 취소, SQL 오류 롤백과 응답 유실, JVM 복구 검사도 유지했습니다. 429의 실제 HTTP 검사는 동시 쓰기를 1건, 고객별 구매와 취소를 각각 분당 2건으로 줄인 조건입니다. 여러 서버의 공동 카운터, 장시간 부하와 DB 서버 자체 종료 복구는 아직 검증하지 않았습니다.
