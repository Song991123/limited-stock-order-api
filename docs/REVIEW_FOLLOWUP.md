# 요청 제한과 재요청 검사 보강

2026년 11월 21일, `63f4a636`의 외부 검토 내용을 코드와 실제 검사에 대조했습니다. 주문과 취소의 저장 SQL, 서비스 트랜잭션과 DB 스키마는 유지하고 요청 제한 결함과 CSRF 입력 정책을 수정했습니다. DB 대조와 롤백 뒤 재요청 검사도 보강했습니다.

## 1. 분이 바뀔 때 요청 횟수가 사라지는 문제

기존 코드는 고객별 잠금을 얻기 전에 `System.nanoTime()`을 읽었습니다. 이전 분의 시각을 읽은 요청이 늦게 진입하면 새 분의 카운터를 이전 분으로 초기화했습니다. 다음 요청은 다시 새 분으로 초기화해 이미 센 횟수를 잃을 수 있었습니다.

수정 전에는 60초, 60초 직전, 60초의 시각을 차례로 전달해 한도가 1회인데 마지막 요청까지 허용되는 것을 확인했습니다. 실제 시계를 뒤로 돌린 것이 아니라 잠금 밖에서 읽은 시각이 늦게 전달되는 순서를 재현한 단위 검사입니다.

`RateWindow`가 잠금을 얻은 다음 시각을 읽도록 바꿨습니다. `LongSupplier`는 검사에서 시각을 바꾸기 위한 용도이며 일반 실행은 계속 `System.nanoTime()`을 사용합니다. 수정 후에는 한 스레드를 실제 모니터 진입 앞에 대기시키고 새 분의 횟수를 먼저 센 뒤 대기 요청이 거절되는지 확인했습니다. 시각 공급 함수가 잠금 안에서 호출되는지도 검사합니다.

고정 1분 구간을 쓰는 정책은 유지합니다. 분이 바뀌기 직전과 직후에 각각 한도만큼 요청할 수 있는 특성은 이번 횟수 소실 결함과 다릅니다. 인증 조회와 BCrypt 계산까지 보호하는 제한도 아닙니다.

## 2. CSRF 헤더 전용 정책 적용

API 명세는 토큰 헤더를 요구했지만 Spring Security 기본 처리기는 URL 파라미터도 받았습니다. 실제 HTTP에서 같은 세션과 유효한 토큰을 쿼리에만 넣은 취소가 200으로 처리되는 것을 재현했습니다. 토큰 없이 통과하는 결함은 아니며 명세와 실제 입력 정책의 차이입니다.

`web.csrf.HeaderCsrfTokenRequestHandler`에서 헤더가 없거나 비면 거절하고 나머지는 기본 XOR 처리기에 맡겼습니다. 토큰 마스킹, 지연 조회와 세션 토큰 검증을 다시 구현하지 않았습니다. HTTP 처리기이므로 계정 변환용 `security`가 아니라 `web.csrf`에 두고 기존 계층 검사도 유지했습니다.

수정 후 쿼리 토큰만 보낸 취소는 403이고 주문은 접수 상태와 재고 9를 유지했습니다. 정상 헤더와 잘못된 쿼리를 함께 보내면 헤더를 기준으로 취소되어 재고 10으로 복구됐습니다. 마스킹 해석, 빈 헤더 거절과 지연 조회는 단위 검사 6건으로 구분했습니다.

[Spring Security CSRF 처리 설명](https://docs.spring.io/spring-security/reference/6.5/servlet/exploits/csrf.html)의 기본 입력 해석과 마스킹 동작을 기준으로 확인했습니다.

## 3. 합계가 맞아도 개별 이력이 틀린 경우 확인

HTTP 검사와 요청 제한 검사에는 주문별 이력의 상품과 증감량 대조가 빠져 있었고 별도 JVM의 `ReviewFixture`에는 들어 있었습니다. 두 주문의 차감량을 서로 바꿔 합계를 유지하자 기존 HTTP 검사는 오류를 잡지 못했습니다. 제품 코드가 잘못된 이력을 만들었다는 재현과는 구분합니다.

`OrderStorageChecks`로 세 경로의 SQL을 공유했습니다. 재고와 합계, 구매 결과와 주문 수, 각 주문의 고객/상품/수량과 이력의 상품/증감량을 함께 봅니다. 수량 교환과 상품 교환을 각각 주입한 검사에서는 전체 합계 위반은 0건이어도 개별 주문 불일치 2건을 잡았습니다. 검사 뒤에는 주입한 값을 되돌립니다.

추가한 것은 검사 도구입니다. 제품 DB에 교차 테이블 트리거를 더 넣거나 모든 운영 요청에서 이 집계 SQL을 실행하지 않습니다.

## 4. 선행 요청 롤백 뒤 대기 요청 확인

첫 HTTP 요청이 구매 기록을 등록한 직후 검사용 DB 잠금에서 기다리게 했습니다. 같은 키의 두 번째 HTTP 요청도 첫 요청 때문에 실제 DB 잠금 대기 중인지 `pg_blocking_pids`로 확인했습니다.

검사용 잠금을 풀면 첫 등록에는 의도한 SQL 오류가 나서 롤백됩니다. 기다리던 요청은 같은 키를 등록하고 주문을 완료했습니다. 세 번 반복해 첫 응답 500, 대기 요청 201, 이후 같은 키의 재요청 200을 확인했습니다. 주문과 차감 이력은 각각 1건, 수량 2 주문 후 재고는 8입니다.

기존 UNIQUE INSERT와 별도 SELECT를 바꾸지 않고 앞선 요청이 커밋하는 경우에 더해 롤백하는 경우의 실제 동작을 검사했습니다. 검사용 정지와 오류 주입은 전용 DB에만 사용하며 제품 코드에 들어 있지 않습니다.

수정 중 새 처리기의 패키지가 기존 계층 규칙에 걸린 실행도 보존했습니다. 처리기를 HTTP용 패키지로 옮겨 해결했으며 검사 규칙을 완화하지 않았습니다. 소스 해시, JUnit 항목과 대표 관찰 값은 [반영 기록](../evidence/verification/review-followup.json), [현재 JUnit 요약](../evidence/verification/junit-summary.xml)에서 대조할 수 있습니다. 원본 XML과 중간 실패 로그는 로컬 `evidence/raw`에 보관합니다.

과거 DB 서버 중단 검사 15건은 재실행하지 않았습니다. 운영 수용량, 장시간 부하, 여러 서버가 공유하는 요청 제한, 잠금 방식별 성능 우위, 구매 기록 만료와 전원 중단 시 저장 장치의 내구성은 미검증입니다. 검사 전용 DB와 자식 JVM만 사용했으며 Bubli와 노션은 변경하지 않았습니다.

## 유지한 구성

주문과 취소의 계층, DTO와 내부 객체 구분, 조건부 UPDATE, 유일성 제약과 서비스 트랜잭션은 유지했습니다. 인덱스 제거, 정확한 시그니처 검사 축소와 단순 주석 정리는 선택 사항이므로 이번 수정에 섞지 않았습니다. `setRollbackOnCommitFailure(false)`의 값은 기본값과 같으며 그 명시 호출만으로 추가 안전성을 얻었다고 설명하지 않습니다.

## 멘토링에서 설명할 핵심

요청 제한은 횟수 증가만 잠가서는 부족했습니다. 시각을 읽는 순서도 함께 보호해야 새 분의 횟수가 사라지지 않습니다. 서버의 주문 정합성은 기존 SQL과 트랜잭션으로 유지하고 이번에는 그 앞의 요청 제한과 토큰 입력 정책을 수정했습니다. 검사에서는 합계에 가려지는 개별 이력 오류와 선행 요청 롤백 뒤의 대기 요청까지 확인했습니다.
