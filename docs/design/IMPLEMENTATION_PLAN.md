# 구현과 검증 계획

구현에 사용한 단계와 후속 비교 계획입니다. 실제 통과 수와 관찰 값은 [검증 기록](../VERIFICATION.md)에 분리합니다.

## 작성과 구현 기준

- 고객 행동, 저장 대상과 실패 조건을 먼저 설명합니다. 내부 식별자와 기술명은 그다음에 연결합니다.
- API 규칙은 'API 명세' 또는 'API 스펙'으로 부릅니다. 그림에는 짧은 동작 표현을 쓰고 '~합니다'를 붙이지 않습니다.
- 제목은 '마지막 재고 처리'처럼 설명형으로 씁니다. 질문형 제목을 쓰지 않습니다.
- 같은 구매의 재전송과 서로 다른 구매의 재고 경쟁을 구별합니다. 자동/수동 구분이나 대기열을 억지로 가져오지 않습니다.
- 실제 구현, 코드 확인, DB 실행 검사와 성능 비교를 나눕니다. 예상 결과를 검증 수치로 쓰지 않습니다.
- 기록은 기존 동작, 변경 코드, 선택 이유, 재현 조건과 결과 순으로 남깁니다. 실패 원인과 부작용도 유지합니다.

## 작업본과 개발 흐름

독립된 `limited-stock-order-api` 작업 폴더에서 구현하고 전용 DB 이름, 자료 경로와 실행 계정을 사용합니다.

새 구현은 develop을 기준으로 `feature/*`, `test/*` 브랜치에서 나누고 검사와 검토 뒤 통합합니다. 실행 가능한 버전만 main에 반영합니다. 지금은 원격 저장소, PR과 배포를 만들지 않습니다.

## P0. 실행 틀과 저장 규칙

산출물: Spring Boot 실행 틀, Java와 의존성 버전 고정, 마이그레이션, 두 시험 계정, 상품/초기 재고, 인증과 API 명세입니다.

조건: JDBC 저장소와 트랜잭션 관리자를 연결하고 UNIQUE, FK, CHECK와 양수 수량을 확인합니다. DB ID를 고객 권한이나 선착순 번호로 취급하지 않습니다. DB/HTTP 대기 한도와 접수 빈도 제한은 측정 전 정책값으로 설정합니다. 실행 비밀 값, 개인 경로와 원시 로그는 Git에서 제외합니다.

## P1. 주문 접수와 재전송

예정 브랜치: `feature/order-acceptance`.

산출물: 상품 조회, 주문 접수, 자기 주문 조회와 목록 API, 요청 키 등록, 조건부 차감과 차감 이력입니다.

조건: 성공 경로뿐 아니라 같은 키의 중복과 내용 불일치, 재고 부족도 구별합니다. DB 오류는 모두 롤백하고 재고 부족 결과는 커밋합니다. 커밋 전에 성공을 응답하지 않습니다. 재전송에서 현재 주문 상태를 반환하며 새 차감을 하지 않습니다.

## P2. 취소와 재고 복구

예정 브랜치: `feature/order-cancellation`.

산출물: 자기 주문 취소 API, 상태 조건부 변경, 복구 이력과 복구 수량 상한입니다.

조건: 상태를 바꾼 요청만 수량을 돌려줍니다. 상태 저장과 재고 복구 사이, 복구와 이력 저장 사이에 오류를 넣어 전체 롤백을 확인합니다. 이미 취소된 주문과 다른 고객 주문의 응답도 구별합니다.

## P3. 실제 요청 중첩과 중단 복구

예정 브랜치: `test/order-concurrency-and-recovery`.

산출물: JUnit 5와 실제 HTTP/격리 PostgreSQL 검사, 요청 순서 제어, 응답 차단과 JVM 중단 검사입니다.

검사에서 임의의 sleep만으로 두 요청이 겹쳤다고 판단하지 않습니다. 서로 다른 DB 연결과 시작 장벽을 사용하고, 잠금을 보유한 별도 연결로 대기 지점을 확인합니다. 시험용 중단과 장애 주입은 운영 서버가 아닌 전용 작업본에만 적용합니다.

기대 결과는 HTTP 응답만이 아니라 주문 수, 요청 기록과 결과, 상태, 재고와 차감/복구 이력을 함께 대조합니다. 상품별 수량 공식은 한 DB 스냅샷에서 읽어 확인하고, 검사 전용 트랜잭션의 미커밋 자료를 다른 연결이 볼 수 있다고 가정하지 않습니다.

## P4. 잠금 비교와 측정

예정 브랜치: `test/order-locking-comparison`.

조건부 UPDATE, SELECT FOR UPDATE 뒤 검사, JPA @Version과 제한 재시도를 같은 상품, 입력과 정확성 조건으로 비교합니다. 잘못된 조회/저장 코드는 결함 재현용이며 빠르다는 이유로 채택 후보에 넣지 않습니다.

HTTP 부하는 k6로 생성하고 주문 수, 오류 종류와 수량 공식은 DB에서 별도로 대조할 계획입니다. 동시 시작만으로 실제 최대 수용량이라 부르지 않습니다. 같은 조건의 반복 실행, 준비 구간과 본 측정 구분, 요청 수, 지연 분포, DB 잠금 대기, 연결 풀과 환경을 함께 남깁니다. [k6의 HTTP 측정 항목](https://grafana.com/docs/k6/latest/using-k6/metrics/reference/)

비교마다 DB 상태를 같은 초기 값으로 되돌리고, 새 구매와 같은 키의 재전송 비율을 기록합니다. 재고가 없어진 뒤 빠르게 거절되는 요청과 실제 주문 성공을 섞어 개선율을 만들지 않습니다. 다른 상품으로 분산된 부하와 한 상품에 몰린 부하를 나눕니다.

먼저 정확성을 확인하고, 그 뒤 처리량과 p95/p99 응답 시간, 거절률과 잠금 대기를 비교합니다. 아직 어느 방식의 우위나 개선율도 측정하지 않았습니다.

## 검사 시나리오

| ID | 재현 조건 | 기대 결과 |
| --- | --- | --- |
| O01 | 재고 1, 서로 다른 고객이 각 1개 동시 주문 | 접수 1건, 재고 부족 1건, 재고 0 |
| O02 | 같은 고객/키/내용을 동시에 전송 | 주문 1건, 차감 1회, 같은 주문 ID |
| O03 | 같은 고객/키에 다른 상품 또는 수량 | 먼저 확정한 입력 유지, 다른 입력은 409, 추가 차감 없음 |
| O04 | 같은 고객/상품/수량, 서로 다른 키, 충분한 재고 | 별도 정상 주문 2건 |
| O05 | 재고 차감 뒤 주문 저장 실패 | 요청과 차감 전체 롤백, 주문/이력 없음 |
| O06 | 주문과 차감 이력 뒤 요청 결과 저장 실패 | 부분 커밋 없음, 같은 키 재시도 가능 |
| O07 | 접수 커밋 뒤 응답 차단 | 같은 키로 같은 주문, 추가 차감 없음 |
| O08 | 재고 부족 확정 뒤 취소로 재고 회복 | 이전 키는 기존 거절, 새 키는 재고 재판정 |
| O09 | 같은 주문의 취소 두 건 동시 실행 | CANCELLED, 복구 1회 |
| O10 | 취소 상태 변경 뒤 재고 복구 실패 | ACCEPTED 유지, 복구 없음 |
| O11 | 재고 복구 뒤 복구 이력 저장 실패 | 상태와 수량 모두 롤백 |
| O12 | 취소와 다른 고객의 새 주문 중첩 | 허용된 확정 순서의 결과, 수량 공식과 범위 유지 |
| O13 | 취소 커밋 뒤 응답 차단과 재요청 | 이미 취소된 주문 반환, 추가 복구 없음 |
| O14 | 취소한 주문의 생성 키로 재전송 | 같은 취소 주문 반환, 새 주문/차감 없음 |
| O15 | 다른 고객의 목록/주문 조회와 취소 | 목록 미노출, 단건 404, 상태/수량 유지 |
| O16 | 재고 기록 잠금이 제한 시간보다 오래 유지 | 503, 신규 요청 저장 없음, 원래 키로 재시도 가능 |
| O17 | 서로 다른 상품의 주문 | 불필요한 전역/계정 잠금 없음 |
| O18 | 접수/취소 각각 커밋 전후 JVM 종료 | 미확정 변경 롤백, 확정 결과 재조회 가능 |
| O19 | 여러 연결의 접수/취소를 반복 | 주문 상태와 두 수량 공식 일치, 중복 이력 없음 |
| O20 | 수량 범위, 없는 상품, 입력 오류와 잘못된 키 | 오류 구분, 주문/수량 변경 없음 |

위 20개는 계획한 검사 조건입니다. 실행 횟수나 통과 수가 아닙니다. 각 행에서 실제 동시성/오류 지점을 확인한 근거와 반복 결과를 별도로 남깁니다.

## 완료할 산출물

- 실행 가능한 독립 Spring Boot 프로젝트와 재현용 요청 스크립트.
- 실패 조건을 포함한 실제 DB 검사와 대표 결과, 원시 기록은 별도 보관.
- 기술 선택의 이유와 비교한 대안, 확인한 한계.
- 문제, 원인, 수정 그림과 결과 중심의 짧은 설명. 설계 자체를 운영 장애 해결 경험으로 쓰지 않음.

P0~P3의 주문/취소 구현, HTTP와 DB 연결 검사, 응답 유실과 별도 JVM 종료/재시작을 실행했습니다. P4의 잠금 방식별 성능 비교와 최대 수용량 측정, 보존량 한도에 따른 접수 중단은 후속 항목입니다.
