# 처리 규칙과 API 명세

주문 API, 상태와 저장 모델의 처리 규칙입니다. 실행 예제와 응답 필드는 [API 명세](../API.md), 검사 결과는 [검증 기록](../VERIFICATION.md)에 정리합니다.

## 1. 주문의 의미

- 구매 고객은 인증 후 상품과 남은 수량을 조회하고 주문합니다. 고객 ID는 인증 정보에서 얻으며 요청 본문으로 받지 않습니다.
- 한 주문은 상품 한 종류와 양의 정수 수량으로 구성합니다. 여러 상품 묶음, 부분 취소, 결제와 배송은 제외합니다.
- 주문 접수는 판매 가능한 수량을 확보하는 단계입니다. 결제 완료나 출고를 의미하지 않습니다.
- 상품과 초기 수량은 시험 데이터로 준비합니다. 첫 범위에는 입고, 관리자 재고 수정과 상품 삭제 API를 두지 않습니다.
- 같은 고객의 별도 구매도 허용합니다. 1인 1개 제한이나 되팔이 방지 정책은 구현 범위가 아닙니다.

## 2. 같은 구매와 새 구매

주문 생성에는 `Idempotency-Key`를 필수로 받습니다. 인증된 고객 ID와 요청 키의 조합을 유일하게 저장합니다. 키는 1~128자의 허용된 영문, 숫자, 하이픈과 밑줄로 제한하고 원문을 로그에 남기지 않습니다. 인증 비밀 값으로 사용하지 않습니다.

| 입력 | 처리 |
| --- | --- |
| 같은 고객, 같은 키, 같은 상품과 수량 | 처음 확정한 주문 또는 재고 부족 결과 반환 |
| 같은 고객, 같은 키, 다른 상품이나 수량 | 409 `IDEMPOTENCY_KEY_REUSED` |
| 같은 고객과 상품이지만 새 키 | 별도 구매로 처리. 재고가 있으면 새 주문 |
| 다른 고객이 같은 문자열 키 사용 | 서로 다른 구매로 처리 |
| 취소한 주문의 원래 키로 재전송 | 원래 주문의 현재 취소 상태 반환. 새 차감 없음 |

클라이언트는 같은 구매의 재시도에 원래 키를 유지해야 합니다. 클릭할 때마다 새 키를 만들면 서버는 별도 구매로 봅니다. 상품과 수량만 해시해 같은 구매로 합치지 않습니다.

재고 부족도 해당 키의 결과로 저장합니다. 이후 다른 고객이 취소해 재고가 생겨도 같은 키는 기존 거절 결과를 반환합니다. 다시 구매하려는 고객은 새 행동에 새 키를 사용합니다. 인증 실패, 형식 오류와 없는 상품은 구매 실행 전에 거절하며 요청 키를 저장하지 않습니다.

## 3. 주문 접수의 저장 범위

인증과 입력 형식, 상품 존재를 확인한 뒤 아래 절차를 하나의 READ COMMITTED 트랜잭션으로 처리합니다.

1. `order_requests`에 고객, 키, 상품과 수량을 등록합니다. 유일성 제약은 `(buyer_id, request_key)`입니다.
2. 이미 같은 키가 있으면 별도 SELECT로 기존 내용을 읽습니다. 같으면 저장된 결과를 반환하고, 다르면 거절합니다. 재고 차감 경로로 내려가지 않습니다.
3. 새 요청은 남은 수량이 충분할 때만 `inventories`의 해당 상품 수량을 차감합니다.
4. 차감에 성공하면 `orders`에 ACCEPTED 주문과 `inventory_movements`에 차감 이력을 저장합니다.
5. 요청 결과를 채우고 커밋한 뒤 HTTP 응답을 보냅니다. 재고가 부족하면 주문은 만들지 않고 요청의 거절 결과만 커밋합니다.

동시에 같은 키를 등록하면 뒤의 INSERT는 앞선 트랜잭션의 확정을 기다릴 수 있습니다. 앞선 요청이 롤백되면 뒤의 요청이 새 등록을 진행할 수 있습니다. 대기 시간이 한도를 넘으면 503으로 종료하며 같은 키로 재시도합니다.

요청 등록을 별도 트랜잭션으로 먼저 커밋하지 않습니다. 저장 중 예외가 나면 요청, 주문, 수량과 이력을 모두 롤백합니다. 결과가 비어 있는 요청 기록은 트랜잭션 안의 임시 상태이며 커밋하거나 작업 대기열로 공개하지 않습니다. 이미 확정된 기록에서 결과가 비어 있다면 정상 재전송으로 처리하지 않고 정합성 오류로 알립니다.

## 4. 취소와 재고 복구

자기 주문만 취소할 수 있습니다. 요청 본문에서 복구 수량을 받지 않고, 저장된 주문의 상품과 수량을 사용합니다. 아래 절차도 하나의 트랜잭션입니다.

1. 자기 주문의 상태가 ACCEPTED일 때만 CANCELLED로 바꿉니다.
2. 실제로 상태를 바꾼 요청만 상품의 판매 가능 수량을 복구합니다.
3. 복구 이력을 저장하고 함께 커밋합니다. 어느 저장이든 실패하면 주문 상태와 수량을 모두 되돌립니다.

이미 CANCELLED라면 200으로 현재 주문을 반환하고 수량을 더하지 않습니다. 취소 두 건이 겹쳐도 같은 상태 조건으로 한 건만 변경합니다. 주문 ID가 취소 대상을 고정하므로 별도 취소 요청 키는 받지 않습니다. POST라는 HTTP 메서드가 이 동작을 자동 보장하는 것은 아닙니다.

취소와 다른 고객의 주문이 겹치면 같은 재고 기록에서 기다릴 수 있습니다. 취소가 반영되기 전에 새 주문이 재고 부족으로 거절되는 결과도 허용합니다. 취소 중이라는 이유로 먼저 수량을 판매하지 않으며, 요청 도착 순서에 따른 공정성은 보장하지 않습니다.

## 5. 상태와 수량 조건

주문 상태는 ACCEPTED와 CANCELLED만 둡니다. 저장이 실패한 신규 주문에는 공개 주문 ID나 주문 상태가 남지 않습니다. 재고 부족은 요청의 거절 결과이지 주문의 FAILED 상태가 아닙니다.

상품별로 다음 조건을 유지해야 합니다. 첫 범위에는 입고나 재고 조정이 없다는 전제입니다.

```text
0 <= 판매 가능 수량 <= 초기 수량
판매 가능 수량 = 초기 수량 - 접수 상태 주문 수량의 합
판매 가능 수량 = 초기 수량 + 확정된 차감/복구 이력의 증감 합
```

차감 이력은 음수, 취소 복구 이력은 양수입니다. 주문별 차감 한 건, 취소 복구 최대 한 건을 유일성 제약으로 제한합니다. 이력만으로 전체 정합성이 자동 보장되지는 않으므로 수량과 주문 상태를 같은 트랜잭션으로 바꿔야 합니다.

## 6. API

| API | 동작과 응답 |
| --- | --- |
| `GET /products`, `GET /products/{productId}` | 상품과 현재 판매 가능 수량. 수량 조회는 구매 예약이 아님 |
| `POST /orders` | 키, 상품과 수량으로 주문. 신규 접수는 커밋 후 201, 같은 구매의 재조회는 200 |
| `GET /orders`, `GET /orders/{orderId}` | 자기 주문 목록과 현재 상태. 다른 고객의 기록 제외 |
| `POST /orders/{orderId}/cancel` | 자기 접수 주문을 취소하고 수량 복구. 이미 취소된 주문도 200 |

입력 예시는 명세 설명용이며 실제 요청 결과가 아닙니다.

```http
POST /orders
Idempotency-Key: example-request-001
Content-Type: application/json

{"productId":101,"quantity":1}
```

최초 접수와 재전송 모두 `id`, `productId`, `quantity`, `status`, `createdAt`, `cancelledAt`을 반환합니다. 재전송은 원래 주문에 연결하되 취소 이후라면 CANCELLED를 반환합니다. 최초 응답의 바이트나 HTTP 상태를 그대로 재생하는 방식은 아닙니다.

| 상황 | 응답과 다음 행동 |
| --- | --- |
| 입력 범위, 알 수 없는 필드나 키 형식 오류 | 400. 같은 입력의 자동 재전송 금지 |
| 인증 또는 CSRF 검사 실패 | 401 / 403. 인증 절차부터 확인 |
| 없는 상품, 없거나 다른 고객의 주문 | 404. 다른 고객의 주문 존재 여부도 노출하지 않음 |
| 같은 키에 다른 내용 | 409 `IDEMPOTENCY_KEY_REUSED`. 기존 요청 유지 |
| 재고 부족 | 409 `OUT_OF_STOCK`. 자동 반복 금지. 새 구매는 새 키 |
| 접수 빈도 또는 동시 처리 한도 초과 | 429와 Retry-After. 같은 구매라면 키 유지 |
| DB 접속 불가, 잠금 대기 한도나 일시적 교착 상태 | 503과 Retry-After. 전체 롤백 후 같은 키로 제한 재시도 |
| 수량 상한 위반 등 예상하지 못한 정합성 오류 | 500. 전체 롤백, 오류 기록. 성공이나 재고 부족으로 숨기지 않음 |

커밋 후 응답이 끊겼다면 성공 여부를 모른다는 뜻입니다. 커밋 중 DB 연결이 끊긴 경우도 롤백됐다고 단정하지 않습니다. 같은 주문 키로 다시 접수해 결과를 확인하고, 취소는 같은 주문 ID로 다시 요청합니다. 시도 횟수와 전체 기한을 제한하고 지연을 둔 재시도 예제를 준비합니다. 무한 재시도나 서버 안의 무제한 재실행은 하지 않습니다.

## 7. 저장 모델 초안

저장 대상과 주요 제약입니다. 실제 DDL은 [V1 마이그레이션](../../src/main/resources/db/migration/V1__orders_and_inventory.sql)에 있습니다.

| 저장 대상 | 주요 내용과 제약 |
| --- | --- |
| `buyers` | 시험 계정의 ID와 인증 정보. 고객 ID는 서버에서 결정 |
| `products` | 상품 ID와 이름. 시험 데이터로 준비하고 주문 중 삭제/변경 API 제외 |
| `inventories` | 상품 FK이자 PK, 초기 수량, 판매 가능 수량. 0 이상과 초기 수량 이하 CHECK |
| `order_requests` | 고객/상품 FK, 요청 키, 수량, 확정 결과. 고객과 키 조합 UNIQUE |
| `orders` | 요청 FK UNIQUE, 고객/상품 FK, 양의 수량, ACCEPTED/CANCELLED, 접수/취소 시각 |
| `inventory_movements` | 주문/상품 FK, 차감 또는 복구 종류, 증감 수량. 주문과 종류 조합 UNIQUE |

주문 수량과 상품은 접수 뒤 바꾸지 않습니다. 결과 ACCEPTED에는 주문 한 건이, OUT_OF_STOCK에는 주문이 없어야 합니다. 고객, 상품과 수량의 연결도 저장 경로와 검사로 확인합니다. FK나 UNIQUE 하나만으로 모든 업무 조건이 검증된다고 설명하지 않습니다.

첫 범위에서는 주문과 요청 키, 이력을 자동 삭제하지 않습니다. 키를 지운 뒤 옛 요청을 다시 보내면 새 주문이 될 수 있기 때문입니다. 보존량 제한과 신규 접수 중단 정책을 설정하고, 운영용 보존 기간과 정리 규칙은 별도 범위로 둡니다.

현재 구현은 요청 빈도와 동시 쓰기를 제한합니다. 기록 전체 보존량에 따른 신규 접수 중단은 후속 구현 항목입니다.
