# 기술 선택과 비용

구현한 처리 방식의 선택 이유와 비용입니다. 동시성, 실패와 재시작은 [실제 검증 기록](../VERIFICATION.md)에 정리합니다. 잠금 방식별 속도 비교와 최대 수용량은 후속 측정 항목입니다.

## 1. 재고 조건과 차감

재고를 먼저 읽고 애플리케이션에서 1을 빼서 저장하면, 두 고객이 모두 1을 읽고 각자 주문을 수락할 수 있습니다. 먼저 읽은 수량이 주문 저장 때도 유효하다고 가정한 것이 문제입니다.

선택안은 대상 상품과 충분한 수량을 WHERE 조건에 둔 UPDATE입니다.

```sql
UPDATE inventories
SET available_quantity = available_quantity - :quantity
WHERE product_id = :productId
  AND available_quantity >= :quantity;
```

변경 1건이면 재고를 확보한 것이고 0건이면 확보하지 못한 것입니다. 상품 존재는 먼저 확인하며 첫 범위에서 상품/재고 삭제를 허용하지 않습니다. 따라서 이 경로의 0건을 재고 부족으로 구별할 수 있습니다.

잠금을 없앤 방식은 아닙니다. PostgreSQL READ COMMITTED에서 같은 재고의 갱신이 겹치면 뒤의 요청은 앞선 트랜잭션의 커밋 또는 롤백을 기다립니다. 커밋 뒤에는 바뀐 수량에 조건을 다시 적용합니다. 이것이 읽기와 차감을 따로 둔 방식과의 차이입니다. [PostgreSQL의 동시 UPDATE 처리](https://www.postgresql.org/docs/16/transaction-iso.html#XACT-READ-COMMITTED)

| 방법 | 첫 선택과 비교할 점 |
| --- | --- |
| 조회 후 값 계산과 저장 | 경쟁 구간이 남아 제외. `@Transactional`만 추가해도 조회 결과가 예약되지는 않음 |
| SELECT FOR UPDATE 뒤 검사/저장 | 유효한 대안. 먼저 잠근 뒤 여러 규칙을 판정할 때 유리하나 현재는 수량 조건 하나여서 별도 조회를 줄이는 안 선택 |
| JPA @Version과 충돌 후 재실행 | 유효한 대안. 버전 충돌의 예외 처리와 제한 재시도가 필요. 어느 쪽이 빠른지는 미측정 |
| 조건부 UPDATE | 수량 검사와 차감을 함께 표현하고 변경 건수로 판정. 같은 상품 경합과 DB 대기는 남음 |
| Redis 분산 잠금 | 재고와 주문은 PostgreSQL에 있어 잠금 수명과 두 저장소의 실패 조건을 추가함. 첫 범위에서는 제외 |

한 주문이 한 상품만 다루는 범위라 짧은 행 단위 처리를 선택합니다. 여러 상품, 결제나 외부 재고가 추가되면 같은 선택을 그대로 확대하지 않습니다. 여러 상품의 갱신 순서와 분산 실패부터 다시 설계해야 합니다.

## 2. 구매 요청의 중복 처리

수량 UPDATE만으로는 같은 구매를 두 번 보내는 것을 막지 못합니다. 재고가 충분하면 두 번 모두 차감될 수 있습니다. 인증된 고객과 요청 키에 유일성 제약을 두고, 이 요청 기록을 먼저 등록한 처리만 차감 단계로 내려갑니다.

등록은 `INSERT ... ON CONFLICT (buyer_id, request_key) DO NOTHING`을 사용합니다. 새 등록이 아니면 다음 SELECT에서 기존 내용을 대조합니다. READ COMMITTED의 한 INSERT가 다른 트랜잭션 때문에 등록되지 않아도, 그 INSERT의 조회 시점에는 상대 기록이 보이지 않을 수 있어 별도 문장으로 재조회합니다. 같은 SQL 안의 조회 결과만으로 없다고 단정하지 않습니다. [INSERT 충돌 처리](https://www.postgresql.org/docs/16/sql-insert.html#SQL-ON-CONFLICT), [격리 수준과 DO NOTHING](https://www.postgresql.org/docs/16/transaction-iso.html#XACT-READ-COMMITTED)

상품과 수량은 작은 고정 입력이므로 정규화한 값을 직접 저장해 대조합니다. 내용 해시만으로 키를 만들면 별도의 정상 구매까지 합칠 수 있어 선택하지 않습니다. 요청 의도와 재시도를 구분해야 한다는 원칙은 [AWS의 멱등 API 설명](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)을 참고합니다.

서버가 받아들인 요청의 결과와 주문 연결을 보존하는 의미의 멱등성입니다. 최초 HTTP 응답 전체를 복사하거나, 새 키로 들어온 주문까지 중복으로 막는다는 의미는 아닙니다. 기록 저장량과 같은 키의 동시 등록 대기가 비용입니다.

## 3. 주문 취소와 재고 복구

취소 전에 상태를 조회하고 나중에 복구하면 두 취소가 모두 접수 상태를 읽을 수 있습니다. 주문 상태 변경에도 조건을 둡니다.

```sql
UPDATE orders
SET status = 'CANCELLED', cancelled_at = CURRENT_TIMESTAMP
WHERE id = :orderId
  AND buyer_id = :buyerId
  AND status = 'ACCEPTED'
RETURNING product_id, quantity;
```

반환된 주문이 있을 때만 그 수량을 복구합니다. 0건이면 자기 주문을 다시 조회해 이미 취소인지, 없는 주문인지 구별합니다. 같은 주문의 동시 취소도 한 요청만 상태를 바꾸므로 재고 복구와 연결할 수 있습니다.

복구 UPDATE는 `available_quantity <= initial_quantity - :quantity`일 때만 덧셈을 허용합니다. 상품이 없거나 복구가 0건이면 정합성 오류로 처리해 취소 전체를 롤백합니다. 정상 취소로 숨기거나 초기 수량을 넘어선 재고를 저장하지 않습니다.

주문 상태는 최소한의 두 상태만 둡니다. 지금은 조건부 상태 변경으로 규칙이 드러나므로 State Pattern이나 상태 머신 제품을 먼저 도입하지 않습니다. 결제 대기, 출고, 반품처럼 전이와 수행 동작이 늘어날 때 다시 비교할 선택입니다.

## 4. 주문과 재고 저장, 오류 처리

주문 접수의 요청 기록, 재고 차감, 주문과 차감 이력은 한 트랜잭션입니다. 취소의 상태 변경, 재고 복구와 복구 이력도 각각 한 트랜잭션입니다. `REQUIRES_NEW`로 일부 저장만 먼저 확정하지 않습니다.

재고 부족은 예상한 업무 결과여서 요청 거절을 저장하고 커밋합니다. 이를 롤백 예외로 던지면 거절 기록도 사라집니다. 접수 서비스가 결과를 반환하고 Controller가 트랜잭션 종료 후 409로 변환하는 안입니다.

SQL이나 제약 오류가 나면 모두 롤백합니다. 컨트롤러가 호출하는 서비스 메서드에 `@Transactional(rollbackFor = Exception.class)`을 붙이고, 저장 오류를 성공 결과로 바꾸지 않습니다. 같은 클래스 안에서 메서드를 호출하는 것만으로 새 트랜잭션 설정이 적용되지는 않습니다. 처리 결과를 채우지 않은 요청은 커밋 시점의 지연 제약 트리거에서도 거절합니다. checked 예외도 롤백하도록 명시했습니다. [Spring의 롤백 규칙](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/rolling-back.html)

응답은 커밋 성공 뒤에 보냅니다. 서버 중단이 커밋 전이면 DB 복구로 미확정 변경이 사라져야 하고, 커밋 뒤 응답 유실이면 같은 요청의 재전송으로 확정 결과를 찾아야 합니다. 커밋 중 연결이 끊기면 확정 여부를 모를 수 있어 같은 키로 확인합니다. 이것은 구현 뒤 실제 프로세스 중단으로 나눠 확인할 조건입니다.

## 5. Spring JDBC 선택 이유

핵심 처리는 조건부 SQL과 변경 건수 확인입니다. Spring JDBC의 `JdbcClient`로 작성하면 어떤 SQL을 실행하고 어떤 데이터를 함께 저장하는지 직접 확인할 수 있습니다. 접수와 취소에 쓰는 저장소는 같은 DataSource와 JDBC 트랜잭션 관리자를 사용합니다. [Spring JDBC와 JdbcClient](https://docs.spring.io/spring-framework/reference/data-access/jdbc/core.html)

첫 구현에는 JPA를 섞지 않습니다. 원시 UPDATE와 JPA의 관리 객체가 다른 값을 갖는 문제까지 함께 다룰 필요가 없고, 현재 모델에는 복잡한 연관관계 탐색도 없습니다. 대신 SQL과 RowMapper, 스키마 변경을 직접 관리하는 비용이 있습니다. JPA가 느리다는 이유로 제외한 것이 아닙니다.

내부 ID는 DB 생성 bigint를 쓰는 안입니다. 연속 번호나 요청 도착 순서를 보장하지 않으며 중간 번호가 비어도 오류가 아닙니다. ID를 알기 어렵게 만드는 대신 모든 주문 조회와 취소에 소유권 검사를 적용합니다.

## 6. 대기 위치와 잠금 범위

요청은 HTTP 처리 중 같은 키의 등록 또는 같은 상품의 재고 갱신에서 DB 확정을 기다릴 수 있습니다. 서버가 별도 작업 대기열에 저장해 나중에 실행하는 구조는 아닙니다. 대기는 DB 잠금 해제 때 이어지며, 제한 시간을 넘기면 해당 트랜잭션을 끝냅니다.

주문은 요청 키 등록, 상품 수량 갱신 순서로 진행합니다. 취소는 자기 주문의 조건부 상태 변경, 상품 수량 갱신 순서입니다. 서로 다른 주문의 취소가 같은 상품에서 잠깐 기다릴 수 있지만 다른 주문 상태 기록을 거꾸로 잠그지는 않습니다. 신규 주문은 아직 다른 요청이 접근할 수 없는 새 ID를 생성합니다. 잠금 범위를 계정 전체나 전체 상품으로 넓히지 않습니다.

예상하지 못한 FK/인덱스 경합과 교착 가능성까지 없다고 단정하지 않습니다. `lock_timeout`, 문장 제한 시간, 연결 풀과 HTTP 동시 처리 한도를 구현 때 고정하고 실제 DB에서 확인합니다. 한도를 넘긴 대기를 재고 부족으로 오인하지 않습니다.

외부 메시지 발행이나 긴 파일 생성이 없어 Outbox와 실행 스케줄러는 첫 선택에서 제외합니다. 상품 한 종류에 몰리는 쓰기는 DB에서 순차 처리되므로 핫 상품의 처리량 한계는 남습니다. 대기열이나 캐시를 추가할지는 그 한계를 측정한 뒤 판단합니다.

## 7. 인증과 요청 수 제한

주문 키는 인증 수단이 아닙니다. 로그인 계정에서 고객 ID를 얻고 목록, 단건 조회와 취소에 모두 소유권 조건을 둡니다. 다른 고객의 주문은 404로 응답합니다. SQL은 파라미터로 바인딩하며 서버가 복구 수량을 결정합니다.

첫 실행은 로컬 시험 계정과 제한된 주소에서 진행합니다. Spring Security의 인증과 CSRF 검사를 요청 스크립트에서도 통과하게 하고, 비밀번호와 DB 연결 비밀 값은 로컬 실행 파일로 분리합니다. 주문 수량의 양수/정수 범위, 본문 크기와 알 수 없는 필드를 검사합니다.

멱등성은 새 키를 계속 만드는 남용이나 매크로 구매를 막지 못합니다. 계정별 요청 빈도와 전체 동시 처리 한도는 별도 정책입니다. 이 숫자는 측정 전 설정값으로 표시합니다. 개인정보, 실제 결제 보안, 운영 수용량과 선착순 공정성은 검증한 범위로 주장하지 않습니다.
