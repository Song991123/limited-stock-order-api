# 동시성 선택과 코드 정리

## 유지한 방식

현재 규칙은 한 상품의 재고 확보, 같은 구매의 재전송과 주문 취소입니다. 재고 조건부 UPDATE, 고객/구매 키 UNIQUE와 서비스 트랜잭션을 유지했습니다. 이 규칙을 SQL로 직접 표현할 수 있다는 판단이며, 다른 방식보다 빠르다고 측정한 결과는 아닙니다.

| 비교한 방식 | 현재 선택과 비용 |
| --- | --- |
| `SELECT FOR UPDATE` 후 검사 | 복잡한 여러 조건을 잠근 뒤 판단할 때 유효. 수량 조건 하나인 현재는 검사와 차감을 UPDATE에 함께 둠 |
| JPA `@Version` | 버전 충돌을 감지한 뒤 전체 트랜잭션을 제한 재실행해야 함. 현재 JDBC 경로에 ORM/재시도를 더할 근거는 부족 |
| `SERIALIZABLE` | 더 넓은 읽기/쓰기 규칙의 정합성에 유효. 직렬화 실패 재시도가 필요하고 도착 순서를 보장하지 않음 |
| `synchronized` | 한 JVM 안의 호출만 제어. 여러 서버나 별도 DB 쓰기를 막는 최종 장치로는 부족 |
| Redis 잠금과 별도 대기열 | DB 밖의 잠금 수명, 재처리와 장애 처리를 추가. 현재 짧은 같은-DB 변경에는 도입하지 않음 |
| `@Async` | 응답과 트랜잭션 실행 스레드가 달라짐. 짧은 접수 SQL의 정확성 문제를 해결하는 대안이 아님 |

PostgreSQL의 조건부 UPDATE도 행 잠금을 사용합니다. 같은 상품에 집중되는 쓰기와 잠금 대기 비용은 남습니다. 여러 상품의 주문, 선착순 보장이나 외부 작업이 필요해지면 규칙과 측정 조건부터 다시 잡아야 합니다. [PostgreSQL 격리 수준](https://www.postgresql.org/docs/16/transaction-iso.html)

## 바꾼 코드

| 기존 | 변경 | 이유 |
| --- | --- | --- |
| 서비스가 HTTP 숫자와 nullable 주문/오류를 조합 | 서비스는 신규/재전송/재고 부족 결과 반환, 컨트롤러는 HTTP 응답 생성 | 주문 처리 코드에 HTTP 상태 코드가 섞이지 않도록 분리 |
| `claim`, `subtract`, 문자열 상태 | `tryRegisterPurchase`, `tryDecreaseStock`, 상태별 enum | 메서드 이름에서 처리와 실패 가능성을 확인, 상태 오타 방지 |
| `OrderModels` 안에 입력/응답/DB 기록 혼합 | 용도별 record와 명시적 import | 파일 이름으로 역할 확인 |
| 보안 설정에서 초기 데이터도 등록 | `SecurityConfiguration`과 `DemoDataInitializer` 분리 | 로그인 설정과 기본 고객/상품 등록 코드를 각각 관리 |
| 컨트롤러 `@Validated` AOP 검증 | MVC 내장 검증과 `@Valid` 유지 | 현재 Spring의 검증 경로 사용, 경로/쿼리 7개 거절 검사 |
| 본문 검사 `@Order(0)` | 인코딩 설정 뒤, 폼/보안 앞에서 원본 크기 검사 | CSRF 폼 파싱으로 검사 본문이 사라지는 조건 차단 |
| 취소 본문을 `@RequestBody byte[]`로 수신 | 검사한 원본 스트림의 본문 존재 확인 | MVC 폼 변환 결과를 빈 본문으로 오인하지 않게 처리 |
| 고객별 분당 한도도 `Retry-After: 1` | 다음 고정 구간까지 남은 초를 올림해 반환 | 한도가 아직 찼는데 즉시 다시 보내는 안내 수정 |

주문 저장소는 하나로 유지했습니다. 주석에는 구매 요청을 먼저 저장하는 이유, 함께 저장할 데이터, 재고를 다시 확인하는 조건과 필터 실행 순서를 적었습니다. 읽는 순서와 어노테이션 선택은 [코드 해설](CODE_GUIDE.md)에서 설명합니다.

## 본문 크기 검사 오류

자기 주문을 만든 고객이 유효한 CSRF 토큰을 폼 본문에 넣고, 8KiB를 넘는 취소 요청을 보냈습니다. 기존 코드의 실제 응답은 413이 아니라 400이었고 재고 9는 유지됐습니다. 취소는 거절됐지만, 크기 검사 전에 CSRF 필터가 폼을 읽어 본문 크기 제한을 먼저 적용하지 못했습니다.

필터 순서를 바꾼 뒤 같은 요청은 413으로 거절되고 재고 9가 유지됐습니다. 다만 중간 수정에서는 작은 폼 본문이 MVC 변환 과정에서 빈 본문처럼 읽혀 취소를 200으로 허용하는 회귀가 발견됐습니다. 취소 API가 원본 본문을 확인하도록 함께 바꿔, 유효한 CSRF 헤더와 함께 보낸 불필요한 본문도 400으로 거절합니다.

기존 코드의 크기 검사 순서 문제와 중간 수정의 회귀를 구분합니다. 다른 고객의 권한을 얻거나 메모리가 유출된 결과로 해석하지 않습니다. [전후 관찰 값](../evidence/verification/input-boundary-comparison.json)에 두 조건을 나누고 최종 통과 결과는 [검증 기록](VERIFICATION.md)에 연결합니다. 원시 실패 로그도 로컬에 보관합니다.

## 판단과 검증의 구분

실행 검사는 실제 HTTP, 전용 PostgreSQL, 잠금 대기 제어, SQL 오류 주입, HTTP 응답 차단과 별도 JVM 종료/재시작을 사용합니다. 타입 분리 자체를 속도 개선으로 계산하지 않습니다. 잠금 방식별 처리량, 응답 시간과 여러 서버의 한도는 아직 비교하지 않았습니다.

현재의 성능 선택을 확정하려면 성공 주문/재고 부족/재전송의 비율을 고정하고 조건부 UPDATE, 명시적 행 잠금과 버전 방식을 같은 조건에서 반복 비교해야 합니다. 먼저 수량, 주문 수와 복원 이력이 같다는 정확성 조건을 통과한 결과만 비교 대상으로 삼습니다.
