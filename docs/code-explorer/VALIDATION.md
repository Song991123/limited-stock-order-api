# 코드 해설 확인

## 11월 21일 요청 제한 수정 반영

요청 제한과 CSRF 입력 정책, 공통 저장값 대조의 원문과 설명을 맞췄다. 변경한 기존 파일 7개와 새 파일 3개만 원문을 대조해 검토 기준을 갱신했다.

| 항목 | 확인 결과 |
| --- | --- |
| 현재 원문 | 81파일, 7,380줄. 문자와 줄 유지 |
| 줄 해설 | 직접 작성한 설명 1,804개, 갱신 필요 0파일 |
| 생성기와 시연 보고서 | Node 검사 44건 통과 |
| 시연 요청 도구 | HTTP 대역 검사 19개. 서버와 DB는 사용하지 않음 |
| 화면 검사 | 별도 화면 없는 브라우저에서 87개 통과. 코드 표시와 검색, 기존 화면 크기 및 새 토큰 처리기 확인 |
| 검사 분류 표시 | 저장된 클래스별 결과에서 정규 수와 분류를 계산. 186건을 HTTP/DB 90건, JVM 복구 1건과 단위/구조 95건으로 표시 |
| 오류와 외부 통신 | JavaScript/CSP 오류 0건, 외부 HTTP/HTTPS 요청 0건 |

데스크톱과 모바일의 검사 표를 캡처해 확인했다. 과거 DB 중단 15건은 별도 기록으로 표시한다. 위 문서 검사는 실제 서비스 JUnit 186건에 더하지 않는다. [문서 확인 결과](validation/review-followup.results.json)와 [서비스 수정 기록](../REVIEW_FOLLOWUP.md)을 구분해 보관한다. 아래 내용은 각 작성 시점의 기록이다.

## 첫 작성본

첫 작성본은 2026-11-18, Windows의 JDK 21.0.10, Node.js 24.14.1과 Chrome 157.0.8103.52에서 확인. 아래 수치와 원시 결과는 첫 작성본의 기록으로 유지한다.

| 항목 | 확인 결과 |
| --- | --- |
| 실제 원문 | 75파일, 6,655줄. BOM과 CRLF만 정규화하고 문자와 줄 유지 |
| 파일별 직접 작성한 줄 해설 | 1,780개. 주석, import와 공통 구문 설명은 별도 |
| 기술과 어노테이션 | 기술 20개, 실제 사용하는 어노테이션 46종의 효과, 이유, 대안과 주의점 |
| 생성기 검사 | 22건 통과. 원문 일치, 메서드 위치, 해설 누락과 변경 감지, HTML 삽입 방지 포함 |
| 브라우저 검사 | 63항목 통과. 원문 75파일의 화면 표시를 원문 데이터와 전부 대조 |
| 화면 크기 | 1440×900, 1280×800, 768×1024, 390×844, 320×780 |
| 화면 동작 | 입력 즉시 검색, 폴더 탐색, 메서드 이동, 어노테이션 설명, 그림 확대, 다운로드와 키보드 이동 |
| 오류와 외부 통신 | JavaScript/CSP 오류 0건, HTTP/HTTPS 요청 0건 |

브라우저에서 캡처한 화면도 확인했다. 320px 탭 넘침은 수정 후 다시 검사했다. 복사는 시스템 클립보드를 바꾸지 않고 대역에 전달한 문자열만 원문과 대조했다.

원문이나 해설을 바꾼 검사 사본에서는 이전 줄 해설이 비활성화되고 최신성 검사가 실패했다. 새 파일의 해설 누락, 삭제 파일의 해설 잔존과 잘못된 줄 번호도 검출했다. 실제 서비스 소스에는 오류를 주입하지 않았다.

[원시 검사 결과](validation/results.json)와 [Node 검사 출력](validation/node-test.tap)에 실행 항목과 문서 해시를 포함한다.

## 보장 범위

이 결과는 코드 해설의 생성과 표시 검사다. 주문 서버, DB나 앱을 새로 실행한 결과가 아니다. 기존 정규 JUnit 172건과 별도 DB 복구 15건에는 더하지 않는다. 제품 코드와 기존 검증 자료는 변경하지 않았다.

소스는 네 묶음으로 나눠 읽었고 주문과 보안 설명은 서로 교차 검토했다. 줄별 설명의 의미를 자동으로 증명하는 검사는 아니다. 코드의 의도나 처리 규칙이 바뀌면 원문과 설명을 사람이 다시 대조해야 한다.

CI에 DB 없는 문서 검사 작업을 추가했지만, 해당 작업의 원격 실행은 하지 않았다. 일반 서비스 검사와 새 문서 검사 수는 별개다.

## 세 곳 수정 후 확인

같은 환경에서 조건문 분류, 갱신 필요 파일의 메서드 설명 차단과 취소 흐름 분리를 검사했다.

| 항목 | 결과 |
| --- | --- |
| 조건문의 SQL 오분류 | 기존 58줄에서 0줄. 실제 SQL과 Java SQL 문자열은 유지 |
| 실행 스크립트의 SQL | 확인한 11줄은 기존 설명을 줄 해설로 보존 |
| 문서 생성기 | 기존 22건에 회귀 검사 14건을 추가한 36건 통과 |
| 문서 화면 | 기존 항목을 포함한 70항목 통과. 취소의 두 경로와 데스크톱/모바일 배치 확인 |
| 갱신 필요 화면 사본 | 별도 5항목 통과. 경고 표시와 옛 파일 설명, 메서드 설명 및 선택 이유의 차단 확인 |
| 원문과 기존 결과 | 원문 75파일, 6,655줄과 기존 서비스 검증 데이터 유지 |

회귀 검사는 문자열을 포함한 Java 조건문, JavaScript/PowerShell 조건문과 실제 SQL을 구별한다. 갱신 필요 상태에서는 해당 파일의 메서드 설명을 숨기고, 정상 파일에서 그 메서드를 호출하는 설명에도 재사용하지 않는다. 해설만 바꿔도 최신성 검사는 실패하며, 검토 기준을 명시적으로 갱신한 뒤에만 다시 표시한다. `--check`는 실패해도 기존 HTML을 덮어쓰지 않는다.

화면 사본은 실제 소스와 검토 기준 파일을 바꾸지 않고 메모리에서 해시 불일치를 모의해 생성했다. 처음 취소와 재취소의 화면 분리는 문서 검사이며 새 주문/취소 API 실행 결과가 아니다. 새 DB 검사와 앱 실행은 하지 않았다.

[추가 원시 결과](validation/three-fixes.results.json)와 [추가 Node 검사 출력](validation/three-fixes.node-test.tap)을 별도로 보관한다. 첫 작성본의 22건/63항목과 기존 서비스 검사 172건 및 DB 복구 15건은 변경하지 않았다.

## GitHub 게시 전 확인

독립 GPT 검토 후 해설 도구의 파일과 메서드 주석을 보완했다. 제품 코드는 `OrderRepository`의 “먼저 요청”을 “먼저 등록한 요청”으로 명확히 한 주석 한 문장만 바꿨다. 주문과 취소 실행문은 유지했다.

HTML을 다시 생성한 뒤 생성기 36건과 화면 70항목이 모두 통과했다. 최신성 검사도 통과했고, JavaScript/CSP 오류와 외부 HTTP 요청은 없었다. 로컬 주문 서버와 DB는 실행하지 않았다.

[게시 전 결과](validation/publication.results.json)와 [Node 검사 출력](validation/publication.node-test.tap)에 현재 HTML과 원문 해시를 따로 남겼다. 앞의 기록과 기존 서비스 검사 수는 유지한다. 원격 CI 결과는 GitHub PR의 Checks와 연결된 실행 기록에서 별도로 확인한다.

## 2026-11-20 실행 파일과 실제 시연

새 전용 PostgreSQL 16.15에서 전체 검사를 실행하고 JAR와 검사 보고서를 다시 만들었다. 주문과 취소의 Java 코드, SQL과 기존 검증 기록은 유지했다.

| 구분 | 확인 결과 |
| --- | --- |
| 전체 JUnit | 172건 통과. 실패, 오류와 생략 0건 |
| 원문과 실행 결과 | 실행 입력 85파일의 해시 일치. 현재 XML 18개가 원시 결과와 바이트 단위로 일치 |
| 실제 HTTP 시연 | 요청 11개와 비교 25개 통과. 재고 10 → 9 → 9 → 10 → 10, 같은 구매의 주문 ID 유지 |
| 데모 DB 재사용 | 서버와 DB 정상 종료 후 같은 DB로 재시작. 기존 주문 ID 1의 CANCELLED와 재고 10 유지 |
| 시연 기록 도구 | Node 생성기 37건과 결과 HTML 변환 7건 통과. HTTP 대역 확인 19항목은 별도 |
| HTML 화면 | 82항목 통과. 실제 시연과 JUnit 보고서 링크, 명령 복사, 320~1440px 배치 확인 |
| 인증값과 종료 | 결과에 실제 비밀번호, 인증 헤더와 쿠키 없음. CSRF 토큰 값 제외. 확인용 서버와 DB 종료 |

이전 결과를 덮어쓰던 복사 절차에서는 옛 XML 3개에 담긴 검사 21건이 남아 합계가 193건으로 읽혔다. 이전 XML과 HTML을 실행별 기록에 보존한 뒤 이번 작업의 폴더만 교체하도록 수정했다. 데모 보고서와 다른 검사 작업은 지우지 않는다. 수정 후 복사된 폴더와 이번 원시 결과가 XML 18개, 검사 172건으로 같아졌다.

실행 준비 중 불완전한 임시 PostgreSQL 도구와 Gradle 캐시도 확인했다. 기존 데이터는 초기화하지 않았고 새 전용 DB를 사용했다. 실패한 준비 실행은 원시 기록에 보존하며 통과 수에 포함하지 않는다.

시연의 실제 요청과 응답, 단계별 재고는 `build/reports/demo/index.html`, 전체 JUnit은 `build/reports/tests/test/index.html`에서 읽는다. 시연에 사용한 JAR 해시도 현재 실행 파일과 대조했다. HTML 해설의 실행과 결과 탭은 이 로컬 파일로 연결하며 명령을 자동 실행하지 않는다.

[이번 실행 기록](validation/execution.results.json)과 [Node 검사 원문](validation/execution.node-test.tap)에 실행 구분과 해시를 보관한다. 기존 DB 중단 복구 15건은 다시 실행하지 않았으며 새 정규 검사, HTTP 시연과 문서 검사 수에 합산하지 않는다. 이 기록은 GitHub 반영 전의 로컬 검사 결과다. 이후 CI 결과는 해당 PR의 Checks와 연결된 실행 기록에서 별도로 확인한다.
