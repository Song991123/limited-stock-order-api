# 검증 기록

2026년 11월 10일, Java 21.0.10, Spring Boot 3.5.16, Gradle 8.14.3과 PostgreSQL 16.15를 사용했습니다. 검사마다 새 로컬 DB를 만들고 실제 HTTP로 요청했습니다.

## 실행 결과

정규 JUnit 154건이 통과했습니다. 실제 HTTP/DB 79건(주문 53, 사용자 행동 13, 일반 실행 1, 두 JVM 12), 별도 JVM 종료/재시작 1건과 단위 검사 74건입니다. 반복과 매개변수별 실행을 포함한 수입니다. 단위 검사는 서비스 26건, 입력 객체 7건, DTO 변환 3건, 자료형 분리 2건, 오류 처리 11건, 인증 실패 응답 3건, 요청 한도 11건과 본문/경로 선택 11건입니다. 기존 135건은 유지했고 19건을 추가했습니다. [JUnit 요약](../evidence/verification/junit-summary.xml)과 [실행 요약](../evidence/verification/latest.json)에서 클래스별 수와 실패 여부를 확인할 수 있습니다. 별도 DB 중단 검사 15건과 k6 실행은 이 수에 합치지 않습니다.

[입력 수정 전후 비교](../evidence/verification/order-safety-comparison.json)는 당시 주문 HTTP 검사 50건씩을 대조합니다. 수정 전 실패 3건은 수정 후 0건입니다. 그때의 전체 109건, 사용자 행동을 추가한 121건, 요청 처리 개선의 135건과 현재 154건은 검사 범위가 다릅니다. 검사 수 증가를 개선율로 계산하지 않습니다. 반복 검사와 매개변수 검사 이름에도 시나리오명을 넣어 같은 회차끼리 구별되도록 했습니다.

사용자 여정을 추가하기 전 코드의 새 전용 DB 실행 `20261110-122502`에서도 109건이 모두 통과했습니다. JUnit XML의 실제 항목 수와 요약 수가 같고, 클래스와 검사명을 함께 비교한 중복도 없었습니다. 취소 커밋 뒤 재시작한 응답은 원래 주문 ID 1, 반환 ID 1, CANCELLED, HTTP 200이며 재고 10과 복구 이력 1건을 유지했습니다. [재검토 결과](../evidence/verification/recheck-20261110.json)는 당시 실행으로 보존합니다.

11월 4일에는 48건에서 60건으로, 11월 9일에는 DTO 검사 등을 포함해 66건으로 늘렸습니다. 11월 10일 수정 직전에도 66건을 다시 통과한 뒤 서비스와 오류 처리, 일반 실행 검사를 추가했습니다. 검사 수 증가를 같은 수의 결함 수정으로 계산하지 않습니다. 재고 SQL, 트랜잭션 설정과 DB 스키마는 유지했습니다.

99건 통과 이후 인코딩 URL, 기존 구매 키의 다른 상품과 중복 JSON 필드를 추가 검사했습니다. 기존 HTTP 검사 47건은 유지됐지만 새 검사 3건은 실패했고, 입력 경로와 판단 순서를 고친 뒤 모두 통과했습니다. 경로 선택 단위 검사 5건과 등록 충돌 뒤 조회 순서 검사 2건도 추가했습니다. [주문 안전성 점검](ORDER_SAFETY_REVIEW.md)에 원인과 비용을 정리했습니다.

서비스 직접 호출 검사 20건을 먼저 추가했을 때 잘못된 ID, 수량과 조회 범위의 12건이 실패했습니다. 컨트롤러 없이 호출한 서비스가 저장소 전에 입력을 거절하는지 보는 대역 검사입니다. 실제 API가 잘못된 수량을 저장했다는 재현은 아니며, 수정 후 20건이 모두 통과했습니다.

11월 9일에는 JDK 구문 분석기로 SQL 관련 문자열 18개와 트랜잭션 어노테이션을 대조했습니다. 11월 10일 99건 검사까지도 두 저장소와 DB 마이그레이션 파일의 해시, 주문 서비스의 트랜잭션 어노테이션이 수정 전과 같은지 확인했습니다. 이후 기존 구매 조회의 반환형과 서비스 호출 순서를 바꿨으며, 재고/취소 SQL과 스키마, 트랜잭션 설정은 유지했습니다. 실제 처리 결과는 HTTP/DB 검사로 따로 확인했습니다.

잘못된 경로/메서드/본문 형식의 404/405/415와 Content-Type을 생략한 본문 없는 취소도 검사했습니다. 실행 스크립트 자체의 별도 관찰은 이전 기록이며, 현재 일반/demo 프로필은 검사 서버와 별도 JVM에서 확인했습니다.

오류 처리 단위 검사에서는 500/503의 응답 번호와 실제 로그 이벤트가 연결되는지 확인했습니다. 로그에 상세 예외 메시지와 SQL 원문이 없고, 줄바꿈이 섞인 SQLSTATE도 기록하지 않는지 검사했습니다. 일반 실행의 별도 관찰 값은 [일반 실행 기록](../evidence/verification/normal-startup.json)에서 확인할 수 있습니다.

고객별 요청 한도의 재시도 안내는 단위 검사로 확인했습니다. 고정 구간의 5초 시점에 한도를 채우면 55초, 구간 끝 직전이면 1초를 반환하며 다음 구간에서 카운터가 초기화됩니다. 실제 서버의 장시간 요청 분산 효과를 측정한 결과는 아닙니다.

[본문 크기 검사 전후 기록](../evidence/verification/input-boundary-comparison.json)은 기존 코드의 400 응답과, 필터 이동 뒤 중간 수정에서 발견한 200 회귀를 별도로 표시합니다. 최종 코드는 두 조건을 각각 413과 400으로 거절했습니다.

20건은 검사용 동시 출발 수입니다. 서버 최대 처리량이나 실제 고객 수를 뜻하지 않습니다. 장벽을 함께 해제하고 `pg_stat_activity`에서 잠금 대기 2건 이상을 확인한 뒤 잠금을 풀었습니다. 같은 상품의 모든 요청이 한순간에 모두 DB에 들어갔다는 뜻도 아닙니다.

## 사용자 행동별 검사

고객의 상품 조회부터 주문 재전송, 취소와 새 키 재구매까지 4개 여정으로 검사했습니다. 품절 뒤 재고가 복구돼도 기존 키의 거절은 유지되고 새 키는 접수됐습니다. 취소 주문이 섞인 자기 목록, 마지막 빈 페이지와 상품 목록의 100개 제한도 확인했습니다.

미인증, 잘못된 비밀번호, 다른 고객의 주문 접근, 고객 ID 조작, CSRF 누락/다른 세션 토큰과 쿠키 삭제는 6개 검사로 확인했습니다. 거절 전후 주문, 구매 기록, 재고와 이력 비교 34회가 모두 일치했습니다. 요청 한도 2개 검사에서는 실제 HTTP 429, 조회 허용, 거절된 키의 재사용과 다른 고객의 독립 구매를 확인했습니다. 동시 쓰기 1건과 고객별 분당 2건으로 한도를 줄인 분기 검사이며 기본 설정의 운영 수용량 측정은 아닙니다.

초기 사용자 행동 추가 뒤 전체 121건과 JAR 빌드, Javadoc이 통과했습니다. [액터별 범위와 실행 방법](ACTOR_VERIFICATION.md), [고객 여정 결과](../evidence/verification/actor-order-journeys.json), [접근 결과](../evidence/verification/actor-access.json), [요청 한도 결과](../evidence/verification/actor-admission.json)를 연결했습니다. 전체 원시 요청과 중간 저장 값은 로컬에 두고 공개 기록에는 대표 결과를 보존합니다. 재고/취소 SQL과 트랜잭션 설정은 유지합니다.

## 큰 요청과 취소 한도 개선

새 조건을 넣은 수정 전 130건 중 4건이 실패했습니다. 알려진 길이가 큰 요청도 스트림을 열었고, Expect 요청의 본문 전송이 시작됐으며, 구매 한도 소진 뒤 취소까지 429로 막혔습니다. 헤더 선검사와 Tomcat의 100 Continue 시점, 구매/취소 횟수 계산을 고친 뒤 같은 130건이 모두 통과했습니다. 정상 Expect 전송과 공통 동시 처리 한도 등을 보는 5건을 더한 전체 135건도 통과했습니다.

8,221바이트 Expect 요청은 전송 시작 1회에서 0회로 바뀌었고 응답은 둘 다 413이었습니다. 구매 한도 뒤 취소는 429/재고 9에서 200 CANCELLED/재고 10으로 바뀌었으며 복구 이력은 1건입니다. [선택 이유와 남은 비용](REQUEST_FLOW_IMPROVEMENTS.md), [동일 조건 전후 결과](../evidence/verification/request-flow-comparison.json)에서 범위를 구분합니다. 속도나 운영 처리량의 개선율을 측정한 결과는 아닙니다.

## 프로세스 종료와 재시작

별도 JVM을 실행해 주문과 취소 각각 커밋 전/후를 나눠 종료했습니다.

| 종료 시점 | 재시작 후 결과 |
| --- | --- |
| 주문의 수량 갱신 대기 중, 커밋 전 | 요청/주문 0건, 수량 10 유지. 같은 키로 정상 접수 |
| 주문 커밋 후 | 원래 주문 ID 반환, 수량 8 유지 |
| 취소의 수량 복구 대기 중, 커밋 전 | ACCEPTED와 수량 8 유지 |
| 취소 커밋 후 | 원래 주문 ID와 CANCELLED 반환, 수량 10, 복구 이력 1건 |

커밋 전 종료는 별도 DB 연결로 수량 갱신을 막고 실제 잠금 대기를 확인한 뒤 JVM을 강제 종료했습니다. 커밋 후 종료는 접수/취소 응답을 확인한 뒤 종료했습니다. HTTP 응답을 잃는 경우는 별도의 응답 차단 검사에서 확인했습니다. 재시작 때 인증 세션과 CSRF 토큰은 새로 발급했습니다.

취소 중단 후 재시작과 취소 확정 후 재시작 모두에서 응답 본문의 주문 ID와 CANCELLED를 직접 검사했습니다. 확정 후 재시작의 HTTP 상태, 예상한 주문 ID와 실제 응답의 ID 및 상태는 [복구 기록](../evidence/verification/process-recovery.json)에 저장했습니다. 검사 항목 수를 늘리지 않고 기존 검사의 확인 조건을 보강했습니다.

## 기록과 재현 방법

`scripts/test.ps1 -IsolatedDatabase`가 입력 소스 해시, JUnit 원문, HTTP 관찰 값과 JVM 로그를 `evidence/raw`에 보관합니다. 공개 요약은 `scripts/export-evidence.ps1`로 만들며, 검사 뒤 소스가 달라지면 내보내기를 거절합니다.

필수 결과 파일이 빠져도 이전 공개 파일을 남기는 문제가 있어 저장 전에 누락 검사를 추가했습니다. 전체 검사 121건을 다시 통과한 뒤, 완료 결과의 복사본에서 고객 여정 파일을 뺀 조건으로 내보내기를 시도했습니다. 내보내기는 실패했고 기존 공개 파일 14개의 해시는 모두 같았습니다. [내보내기 검사](../evidence/verification/publication-check.json)는 검사 도구의 확인 결과이며 JUnit 121건에 포함하지 않습니다.

관찰 값은 [HTTP/DB 결과](../evidence/verification/observations.json)와 [재시작 결과](../evidence/verification/process-recovery.json), 검사 입력은 [소스 해시](../evidence/verification/source-sha256.json)로 대조합니다. 기존 HTTP 기록의 일부 값은 단언 통과 뒤 예상 상수로 저장하므로 독립 측정값과 구분합니다. 새 사용자 검사에는 응답에서 읽은 값과 DB 조회값을 기록합니다. 원시 로그와 실행 비밀 값은 로컬에 보관합니다.

GitHub Actions는 별도 Linux 실행기와 임시 PostgreSQL 16으로 같은 JUnit 검사, JAR 빌드와 Javadoc을 실행합니다. 이 문서의 로컬 결과와 CI 실행 결과는 구분하며 PR의 검사와 보고서에서 해당 커밋의 실제 통과 여부를 확인할 수 있습니다. CI에는 서버 배포 단계가 없습니다.

PR 검토에서 일반 실행 검사의 고정 스키마가 같은 시험 DB의 다음 실행과 충돌하는 조건을 확인했습니다. 실행마다 다른 스키마를 만들고 종료 시 직접 만든 스키마만 제거하도록 수정했습니다. 같은 전용 DB 프로세스를 유지한 두 실행이 모두 통과했고, 남은 검사 스키마는 각각 0개이며 별도 확인용 데이터 777은 유지됐습니다. [반복 실행 기록](../evidence/verification/startup-repeat.json)은 별도 확인이며 최종 JUnit 수에 다시 더하지 않습니다.

초기 검사에서 재고 0인 새 주문까지 잠금을 기다린다고 가정한 조건이 실패했습니다. 해당 주문은 즉시 거절되므로, 미확정 취소 중 거절과 취소 확정 후 접수를 나누어 검사하도록 바로잡았습니다.

## 후속 항목

- 조건부 UPDATE, SELECT FOR UPDATE와 JPA 버전 방식의 성능 비교.
- 장시간 부하, 최대 수용량과 여러 서버에서 공유하는 요청 한도.
- 기록 보존량 한도와 정리 이후 재요청 정책.

현재 결과는 로컬 시험 계정과 위 실패 조건의 기능/정합성 검사입니다. 성능 개선율이나 운영 수용량을 측정한 결과로 확대하지 않습니다.

## DB 중단과 두 JVM

DB를 중단하는 검사는 정규 `test`에서 제외하고 `databaseRecoveryTest`로 따로 실행합니다. 주문/취소의 마지막 저장 후 커밋 직전은 검사 전용 지연 트리거와 advisory lock으로 멈췄고, 해당 JVM 연결의 실제 잠금 대기를 확인한 뒤 전용 DB만 immediate 모드로 중단했습니다. 확정 후에는 프록시가 실제 서버 응답을 받고 클라이언트에는 전달하지 않은 상태에서 DB를 중단했습니다.

같은 5조건을 각각 3회 검사했습니다. 수정 전에는 커밋 전 중단 6회가 500, 인증 저장소 중단 3회가 401이어서 9건이 실패했습니다. 인증 실패 응답 분리와 커밋 오류 보존 후 15건이 통과했습니다. 재시작한 것은 DB이며 서버 JVM은 유지했습니다. 재고와 주문/이력 정합성은 수정 전후 모두 유지됐습니다. 새로 발견한 데이터 중복이나 인증 우회로 표현하지 않습니다.

두 JVM은 각각 별도 HTTP 포트와 연결 풀 4개를 사용했습니다. 같은 구매 20회, 마지막 재고, 같은 취소 20회와 취소/새 구매 중첩을 각각 3회 확인했습니다. 새 주문과 복구는 한 번만 남았고 수량/이력 대조도 일치했습니다. 기본 실행의 풀 12개를 바꾼 것이 아니며, 공통 요청 한도나 세션 공유를 검증한 것도 아닙니다.

[점검표와 선택 이유](BACKEND_REVIEW.md), [DB 중단 및 부하 대표 결과](../evidence/verification/backend-review.json), [두 JVM 결과](../evidence/verification/two-servers.json)에 정규 검사와 별도 실행의 범위를 구분합니다. DB 중단 검사는 로컬 전용 명령이며 GitHub CI의 통과 수에 더하지 않습니다.

`latest.json`의 범위는 정규 검사 한 번입니다. 별도 DB 중단과 부하는 `backend-review.json`에서 확인합니다. 부하 실행 뒤 기존 XML의 BOM 처리 때문에 내보내기 스크립트만 수정했습니다. 공개 기록에는 이 파일의 실행 당시/현재 해시를 둘 다 남기고, 제품 코드와 k6 및 실행기는 같다는 것을 대조합니다. 원시 측정 파일은 고치지 않았습니다.

완료 전 2초 예비 실행과 수집기 해시를 바꾼 검사 전용 사본은 내보내기에서 거절됐고, 기존 공개 결과의 해시도 유지됐습니다. [내보내기 보호 검사](../evidence/verification/review-publication-check.json)는 JUnit 수와 별개의 검사 도구 확인입니다.

## 코드 주석 검사

초기 코드의 주석 검사는 JDK 21의 JavaCompiler와 DocTrees로 구문 트리를 읽었습니다. 당시 주 코드 19개 파일의 타입 선언 27개, 직접 작성한 메서드와 생성자 76개에 Javadoc 누락이 없었습니다. record의 자동 생성 접근자 같은 암묵적 메서드는 이 수에 포함하지 않습니다. 이 수는 패키지 정리 전 코드 기준이며, 현재 코드의 주석 수를 다시 집계한 결과는 아닙니다.

전체 빌드의 Javadoc 작업도 통과했습니다. private 선언까지 설명서를 생성하고 잘못된 태그, 문법과 문서 내 참조는 doclint로 검사했습니다. 단순 필드/자동 생성 선언의 누락 경고는 제외하고 나머지 경고는 실패로 처리합니다. 이는 주석의 존재와 형식 확인이며, 설명이 업무 규칙과 일치하는지는 코드와 HTTP/DB 회귀 검사로 따로 대조합니다. [주석 검사 기록](../evidence/verification/documentation.json)에서 실행 범위를 확인할 수 있습니다.
