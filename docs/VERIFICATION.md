# 검증 기록

2026년 11월 4일, Java 21.0.10, Spring Boot 3.5.16, Gradle 8.14.3과 PostgreSQL 16.15를 사용했습니다. 검사마다 새 로컬 DB를 만들고 실제 HTTP로 요청했습니다.

## 실행 결과

최종 코드의 JUnit 실행은 47건이며 반복 검사를 포함합니다. HTTP/DB 39건, 별도 JVM 종료/재시작 1건과 쓰기 한도/응답 단위 검사 7건이 모두 통과했습니다. 정확한 실행 시각은 [JUnit 요약](../evidence/verification/junit-summary.xml), [실행 요약](../evidence/verification/latest.json)에 남깁니다.

잘못된 경로/메서드/본문 형식의 404/405/415와 Content-Type을 생략한 본문 없는 취소도 검사했습니다. 실제 실행 스크립트의 주문, 재전송과 중복 취소 결과도 별도로 확인합니다.

| 조건 | 관찰 결과 |
| --- | --- |
| 마지막 재고 1개에 서로 다른 고객의 주문 2건 | 접수 1건, 재고 부족 1건, 남은 수량 0. 세 번 반복 |
| 같은 구매 키로 20건을 동시 출발 | 신규 201 한 건, 기존 주문 200 열아홉 건. 주문/차감 각각 한 번. 세 번 반복 |
| 같은 주문 취소 20건을 동시 출발 | 모두 취소 결과 200, 수량 복구와 복구 이력은 한 번. 세 번 반복 |
| 재고 차감 뒤 주문/요청 결과/이력 저장 실패 | 전체 롤백. 요청과 주문이 남지 않고 수량 유지 |
| 취소 상태 변경 또는 수량 복구 뒤 저장 실패 | 접수 상태와 차감된 수량 유지. 재시도에서 한 번만 복구 |
| 재고 0인 주문의 취소를 미확정으로 유지하고 새 주문 | 취소 확정 전 409, 취소 확정 후 새 키로 201 |
| 서버 커밋 후 HTTP 응답 차단 | 주문 재전송에 같은 주문, 취소 재요청에 추가 복구 없음 |
| 재고 잠금이 3초 한도를 넘김 | 503과 Retry-After, 미완료 요청 없음. 같은 키로 다시 접수 성공 |
| 다른 고객의 주문 조회/취소 | 404, 해당 주문과 수량 유지 |
| 큰 본문, 소수/문자열 수량, 임의 고객 ID | 입력 거절, 주문과 수량 변경 없음 |
| 8KiB 초과 폼 본문과 유효한 폼 CSRF 토큰 | 기존 400 대신 크기 검사에서 413, 주문과 재고 9 유지 |
| 유효한 CSRF 헤더와 비어 있지 않은 취소 폼 | 400, 주문과 재고 9 유지. 폼 본문의 토큰만 보내면 403 |
| 경로/쿼리의 잘못된 값 7개 | MVC 내장 검증에서 400, 주문/수량 변경 없음 |

고객별 요청 한도의 재시도 안내는 단위 검사로 확인했습니다. 고정 구간의 5초 시점에 한도를 채우면 55초, 구간 끝 직전이면 1초를 반환하며 다음 구간에서 카운터가 초기화됩니다. 실제 서버의 장시간 요청 분산 효과를 측정한 결과는 아닙니다.

[입력 경계 전후 기록](../evidence/verification/input-boundary-comparison.json)은 기존 코드의 400 응답과, 필터 이동 뒤 중간 수정에서 발견한 200 회귀를 별도로 표시합니다. 최종 코드는 두 조건을 각각 413과 400으로 거절했습니다.

20건은 검사용 동시 출발 수입니다. 서버 최대 처리량이나 실제 고객 수를 뜻하지 않습니다. 장벽을 함께 해제하고 `pg_stat_activity`에서 잠금 대기 2건 이상을 확인한 뒤 잠금을 풀었습니다. 같은 상품의 모든 요청이 한순간에 모두 DB에 들어갔다는 뜻도 아닙니다.

## 프로세스 종료와 재시작

별도 JVM을 실행해 주문과 취소 각각 커밋 전/후를 나눠 종료했습니다.

| 종료 시점 | 재시작 후 결과 |
| --- | --- |
| 주문의 수량 갱신 대기 중, 커밋 전 | 요청/주문 0건, 수량 10 유지. 같은 키로 정상 접수 |
| 주문 커밋 후 | 원래 주문 ID 반환, 수량 8 유지 |
| 취소의 수량 복구 대기 중, 커밋 전 | ACCEPTED와 수량 8 유지 |
| 취소 커밋 후 | CANCELLED 반환, 수량 10, 복구 이력 1건 |

커밋 전 종료는 별도 DB 연결로 수량 갱신을 막고 실제 잠금 대기를 확인한 뒤 JVM을 강제 종료했습니다. 커밋 후 종료는 접수/취소 응답을 확인한 뒤 종료했습니다. HTTP 응답을 잃는 경우는 별도의 응답 차단 검사에서 확인했습니다. 재시작 때 인증 세션과 CSRF 토큰은 새로 발급했습니다.

## 기록과 재현 방법

`scripts/test.ps1 -IsolatedDatabase`가 입력 소스 해시, JUnit 원문, HTTP 관찰 값과 JVM 로그를 `evidence/raw`에 보관합니다. 공개 요약은 `scripts/export-evidence.ps1`로 만들며, 검사 뒤 소스가 달라지면 내보내기를 거절합니다.

관찰 값은 [HTTP/DB 결과](../evidence/verification/observations.json)와 [재시작 결과](../evidence/verification/process-recovery.json), 검사 입력은 [소스 해시](../evidence/verification/source-sha256.json)로 대조합니다. 원시 로그와 실행 비밀 값은 로컬에 보관합니다.

초기 검사에서 재고 0인 새 주문까지 잠금을 기다린다고 가정한 조건이 실패했습니다. 해당 주문은 즉시 거절되므로, 미확정 취소 중 거절과 취소 확정 후 접수를 나누어 검사하도록 바로잡았습니다.

## 후속 항목

- 조건부 UPDATE, SELECT FOR UPDATE와 JPA 버전 방식의 성능 비교.
- 장시간 부하, 최대 수용량과 여러 서버에서 공유하는 요청 한도.
- PostgreSQL 서버 자체 중단과 복구.
- 기록 보존량 한도와 정리 이후 재요청 정책.

현재 결과는 로컬 시험 계정과 위 실패 조건의 기능/정합성 검사입니다. 성능 개선율이나 운영 수용량을 측정한 결과로 확대하지 않습니다.
