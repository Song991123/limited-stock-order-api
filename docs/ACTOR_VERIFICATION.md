# 사용자 행동별 검증

고객이 상품을 조회하고 구매한 뒤 취소하거나 다시 구매하는 흐름을 실제 HTTP와 PostgreSQL로 검사합니다. API 요청은 고객별 인증과 세션을 사용하고, JDBC는 시험 데이터 준비와 저장 결과 대조에만 사용합니다.

## 액터와 행동

| 액터 | 요청 순서와 확인 대상 | 검사 코드 |
| --- | --- | --- |
| 구매 고객 | 상품 조회 → 주문 → 같은 구매 재전송 → 내 주문 조회 → 취소 → 반복 취소 → 새 구매. 주문 ID, 상태, 재고와 증감 이력 대조 | [고객 여정](../src/test/java/dev/mentoring/orders/ActorOrderJourneyIntegrationTest.java) |
| 다른 구매 고객 | 타인 주문의 목록 노출, 상세 조회와 취소 거절. 같은 문자열의 구매 키를 써도 자기 주문으로 분리 | [접근 권한](../src/test/java/dev/mentoring/orders/ActorAccessIntegrationTest.java) |
| 미인증 호출자 | 노출된 API 7개의 인증 없는 요청과 잘못된 비밀번호 요청 거절. 거절 뒤 주문, 구매 기록과 재고 불변 | [접근 권한](../src/test/java/dev/mentoring/orders/ActorAccessIntegrationTest.java) |
| 동시에 구매하는 고객 | 마지막 재고 경쟁, 같은 구매 20건, 같은 주문 취소 20건, 주문과 취소 혼합 후 수량과 이력 대조 | [동시 요청](../src/test/java/dev/mentoring/orders/OrderHttpIntegrationTest.java) |
| 한도에 도달한 고객 | 429와 재시도 안내, 거절된 구매 키 미저장, 조회 허용과 다른 고객의 독립 구매 | [요청 한도](../src/test/java/dev/mentoring/orders/ActorAdmissionIntegrationTest.java) |

다른 고객과 동시 구매 고객은 새로운 서버 권한이 아니라 같은 CUSTOMER 권한을 가진 서로 다른 사용자입니다.

## API와 상태별 확인

| API 또는 상황 | 확인 내용 |
| --- | --- |
| `GET /csrf` | 인증 뒤 토큰 발급. 변경 요청은 같은 세션의 토큰 사용 |
| `GET /products`, `GET /products/{id}` | 상품과 현재 재고 조회, 미존재 상품 거절. 조회는 재고 예약이 아님 |
| `POST /orders`, 새 키 | 충분한 재고면 새 주문, 재고 부족이면 거절 결과만 저장 |
| 같은 고객의 같은 구매 키 | 상품과 수량이 같으면 같은 주문 반환. 다르면 409로 거절 |
| 취소된 주문의 구매 키 | 같은 취소 주문 반환. 주문 부활이나 추가 차감 없음 |
| 품절로 거절된 구매 키 | 재고가 복구돼도 거절 유지. 새 키는 현재 재고로 다시 판단 |
| `GET /orders` | 자기 주문만 ID 내림차순으로 조회. 취소 주문도 포함, 거절된 구매는 주문으로 표시하지 않음 |
| `GET /orders/{id}` | 자기 주문의 접수/취소 상태 확인. 타인 주문과 없는 주문은 404 |
| `POST /orders/{id}/cancel` | 접수 주문만 취소와 복구를 함께 저장. 반복 취소는 복구를 반복하지 않음 |
| 잘못된 입력과 취소 본문 | 입력 거절 뒤 주문, 구매 키와 재고 불변. 정상 입력으로 같은 키 재사용 |
| CSRF 누락, 다른 세션 토큰, 쿠키 삭제 | 주문과 취소를 거절. 새 세션과 토큰을 받은 뒤 정상 요청 |
| 같은 문자열의 구매 키를 쓰는 두 고객 | 각자 주문을 만들고 자기 주문만 조회/취소 |
| 저장 오류와 HTTP 응답 유실 | 롤백 또는 확정된 기존 결과 확인. 같은 구매 키/주문 ID로 재요청 |
| 주문 API 프로세스 종료 | 커밋 전/후를 구분해 재시작. 원래 주문 ID와 CANCELLED, 수량과 복구 이력 확인 |
| 쓰기 동시 처리 한도 | 앞선 요청이 대기할 때 후속 쓰기는 429. 상품 조회는 가능하며 거절된 키는 저장하지 않음 |
| 고객별 요청 횟수 한도 | 구매와 취소 횟수는 따로 계산. 같은 구매 재전송도 구매 횟수에 포함. 구매 한도 뒤 취소 허용, 반복 취소의 한도는 유지 |
| 알려진 큰 본문과 Expect 요청 | 헤더에서 큰 길이를 확인하면 본문 전송 허용 전에 거절. 정상 Expect와 정확히 8192바이트 입력은 접수 |

새 검사는 위 API의 연속 행동과 접근 조건을 보강합니다. 기존 입력, SQL 오류 주입, 응답 유실과 재시작 검사는 유지합니다. 각 요청 뒤 응답만 확인하지 않고 주문, 구매 결과, 판매 가능 수량과 차감/복구 이력을 함께 대조합니다.

## 실행과 근거

고객 여정, 접근 권한과 요청 한도는 각각 새 전용 DB에서 실행하고, 마지막으로 전체 검사와 JAR 빌드, Javadoc을 함께 실행합니다. 여러 검사 실행기가 같은 빌드 결과를 덮어쓰지 않도록 순서대로 실행합니다.

| 초기 추가 검사 | 개별 실행 | 대표 결과 |
| --- | --- | --- |
| 고객 여정 4건 | `20261110-133143`, 모두 통과 | 같은 구매는 ID 1 유지, 취소 후 새 구매는 ID 2. 취소 주문 재전송은 CANCELLED, 재구매 뒤 재고 7 |
| 접근 권한 6건 | `20261110-132254`, 모두 통과 | 미인증/오인증 GET 401, 토큰 없는 POST 403. 타인 주문 404. 거절 전후 DB 비교 34회 모두 일치 |
| 요청 한도 2건 | `20261110-131913`, 모두 통과 | 동시 쓰기 거절 429 뒤 같은 키 재접수 201. 같은 구매 반복은 201→200→429, 다른 고객 주문은 201 |

개별 실행 수를 최종 전체 실행 수에 다시 더하지 않습니다. 요청 한도의 분 초기화 시점에 따라 429가 나오는 반복 횟수는 달라질 수 있으며, 검사도 특정 회차가 아니라 한도 거절과 중복 차감 방지를 확인합니다.

이후 구매 한도 소진 뒤 취소를 허용하는 검사를 추가해 사용자 행동은 총 13건입니다. 최종 `20261110-142000`에서 전부 통과했고 취소는 200 CANCELLED, 재고 10과 복구 이력 1건을 유지했습니다. 큰 요청과 정상 Expect 조건은 주문 HTTP 검사에 추가했습니다. [전후 결과와 한도 분리 이유](REQUEST_FLOW_IMPROVEMENTS.md)

```powershell
.\scripts\test.ps1 -IsolatedDatabase -TestsOnly -TestFilter dev.mentoring.orders.ActorOrderJourneyIntegrationTest
.\scripts\test.ps1 -IsolatedDatabase -TestsOnly -TestFilter dev.mentoring.orders.ActorAccessIntegrationTest
.\scripts\test.ps1 -IsolatedDatabase -TestsOnly -TestFilter dev.mentoring.orders.ActorAdmissionIntegrationTest
.\scripts\test.ps1 -IsolatedDatabase
```

새 사용자 검사 기록은 응답에서 읽은 값과 DB 조회값을 저장합니다. CSRF 토큰, 쿠키와 비밀번호는 공개하지 않습니다. 기존 HTTP 기록에는 단언 통과 뒤 예상 상수를 저장한 항목도 있으므로 모든 JSON 값을 별도로 수집한 측정값으로 해석하지 않습니다. 최종 실행 수와 기존 109건의 재검토는 [검증 기록](VERIFICATION.md)에서 구분합니다.

## 확인 범위

화면이 없는 API 프로젝트의 사용자 행동 검사입니다. 고객의 요청은 실제 HTTP로 보내며 제품 화면을 조작한 검사는 아닙니다.

429 검사는 동시 쓰기를 1건, 고객별 구매와 취소를 각각 분당 2건으로 줄여 분기와 저장 결과를 확인합니다. 기본 설정인 공통 32건/종류별 120회의 수용량 측정은 아닙니다. 시간이 지나 분당 카운터가 초기화되는 조건은 기존 단위 검사로 확인하며, 실제 HTTP에서 1분을 기다려 재개하는 검사는 포함하지 않습니다.

API와 대표 상태를 기준으로 범위를 정했습니다. 모든 입력 문자열, 헤더 중복과 경로 조합을 열거한 보안 검사는 아닙니다. 이후 별도 검사에서 두 JVM의 DB 중복 방지와 DB 서버 중단 복구를 확인했습니다. [추가 점검표](BACKEND_REVIEW.md)에 해당 범위를 구분합니다. 여러 서버의 공통 요청 한도, 장시간 부하와 CSRF 세션의 시간 만료는 미검증입니다.
